## 三、Q&A 准备（3分钟，10个高概率问题）

### 第一类：技术类

**Q1：为什么选择 OpenClaw 而不是直接调 DeepSeek API？**
> 选 OpenClaw 是因为它提供了智能体的 Skill 组合和状态管理能力。  
> 我们把认知分析、书架推荐、苏格拉底追问分别封装为三个独立的 OpenClaw Skill，  
> 每个 Skill 有自己的 prompt 和工作流，OpenClaw 负责协调调用。  
> 这样比直接调 API 更模块化，也更符合赛题对智能体框架的要求。

**Q2：采集小红书数据会不会有法律风险？**
> 我们只采集用户自己浏览的公开页面 DOM 信息，不抓取他人的私人数据，  
> 不绕过任何登录验证，不做爬虫批量请求。这类"用户为自己抓取自己所见内容"的操作，  
> 在法律上属于用户的合法行为，类似于用户自己截图记录。  
> 所有数据存在用户本地，不上传。

**Q3：DeepSeek 分析结果的准确性怎么保证？**
> 我们在 prompt 工程上做了几个设计：  
> ①要求分析"内容的倾向"而非"用户的立场"，降低主观误判；  
> ②对互动类型加权，点赞/收藏比普通浏览权重更高；  
> ③要求 DeepSeek 输出结构化 JSON，降低幻觉风险（用 `response_format: json_object`）。  
> 当然，LLM 本身有局限，我们在报告页也标注了"AI辅助分析，仅供参考"。

**Q4：如果小红书改版了，DOM 选择器会不会失效？**
> 是的，这是浏览器扩展天然的脆弱性。  
> 我们的应对方案是：content.js 里的选择器做了多重备选，同时在后台添加了错误上报，  
> 一旦采集失败会在 Dashboard 提示用户。  
> 长期方案是引入 CSS 选择器配置化，通过远程配置更新选择器，无需重新发布扩展。

---

### 第二类：产品/商业类

**Q5：和现有的"数字健康"APP 有什么区别？**
> 市面上的数字健康工具（比如屏幕时间统计）关注的是"用多久"，  
> 我们关注的是"看了什么"——这是本质不同。  
> 更重要的是，推荐算法的目标是让你更多消费，我们的目标是帮你走出信息茧房。  
> 我们不推送内容，不设红点，用户主动来看，而不是被动接收。

**Q6：商业化怎么做，用户愿意付费吗？**
> 目标用户是对信息质量有较高要求的人：大学生、知识工作者、媒体从业者。  
> 个人订阅制，定价参考 Notion（约68元/月），核心卖点是"认知健康"这个新品类。  
> 企业版面向品牌方和公关公司，帮助他们分析目标受众的信息偏好，单价更高。

**Q7：数据存本地是优点还是缺点？** （可能被问到）
> 优点：隐私保护是我们的核心卖点，本地存储确保数据不外泄；  
> 对目标用户群（高知、注重隐私的人）是加分项。  
> 缺点：换设备后数据不同步，暂时没有多设备方案。  
> 中期计划提供可选的加密云同步（用户授权），不强制上传。

---

### 第三类：细节类

**Q8：苏格拉底追问是真的不给建议吗，会不会用户感到沮丧？**
> 是的，设计上智能体只追问不下结论，目的是保护用户的自主判断权。  
> 但我们设置了安全阀：如果用户3次以上要求给出观点，智能体会说"我更相信你自己想清楚这个问题"，  
> 不会无限追问让用户感到被绕圈。

**Q9：为什么用 SQLite 而不是更强的数据库？**
> 项目定位是本地工具，单用户使用，数据量不大（一周几十条记录）。  
> SQLite 足够应付，而且无需安装数据库服务，对用户友好。  
> 如果未来做 SaaS 版，会迁移到 PostgreSQL。

**Q10：两个人分工怎么做的，AI 工具在项目里扮演什么角色？**
> 我们用的是 vibe coding 模式：  
> 后端由 Claude 辅助编写，我负责需求描述、架构决策、验收测试；  
> 前端由 GitHub Copilot 辅助编写，队友负责 UI 设计和交互逻辑。  
> AI 写代码，人来做判断——这也契合我们项目的理念：工具辅助，人做决定。
