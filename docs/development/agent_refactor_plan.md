# EatWhat 智能体化重构方案

> 本文件总结 2026-07-27 关于 EatWhat 赛后方向的讨论结论，用于团队内部同步。

---

## 一、我们决定了什么方向

### 1.1 不做「通用智能体框架」

通用框架（如 LangChain、LlamaIndex、AutoGen）的问题是：

- 没有独特定位，做出来也是玩具；
- 竞争太激烈，需要极强的工程成熟度；
- 要适配无数场景，工作量无边界；
- 对大一零基础团队风险过高。

### 1.2 也不做「简单 API 调用应用」

如果直接把 OpenClaw 换成 FastAPI 调 DeepSeek：

- 和用户现在的体验没区别；
- 复刻成本低，没有技术壁垒；
- 只是换了个后端，没有解决「被框架锁定」的本质问题。

### 1.3 最终方向：自包含的认知健康智能体应用

**EatWhat 自己就是一个 Agent。**

- 有自己的 Agent 运行时（观察、计划、行动、反思）；
- 直接调用 DeepSeek / OpenAI / Ollama 等模型 API；
- 不依赖 OpenClaw、Hermes、LangChain 等任何外部 Agent 框架；
- 专注于「认知健康 / 反信息茧房」这一个垂直场景；
- 用户可以低门槛本地运行。

**一句话**：把 EatWhat 从一个「调用外部框架的应用」升级为一个「自带大脑的独立智能体」。

| 模块 | 可沿用程度 | 说明 |
|---|---|---|
| `backend/models.py` + SQLite 数据库 | **80%** | 5 张表结构基本不变，可能增加记忆相关表 |
| `backend/routers/` 路由结构 | **70%** | API 路径保留，但后端逻辑从「被动响应」变成「Agent 触发/查询」|
| 浏览器扩展 `extension/` | **80%** | content.js / background.js 采集逻辑基本可用，可能增加更多事件上报 |
| 前端 `frontend/` | **70%** | 4 个页面保留，增强 proactive 提醒、对话历史、趋势图等 |
| 日志系统 `backend/logger.py` | **90%** | 沿用，Agent 运行日志更重要 |

| 业务逻辑（报告/书架/冷静期）| **60%** | 逻辑保留，但执行方式从 Skill 变成 Agent 可调用的工具 |

## 三、需要新增 / 重构的内容

### 3.1 Agent 运行时核心（Agent Runtime）

这是整个重构的心脏。

需要实现：

```
用户输入 / 时间触发 / 事件触发
    ↓
[感知模块] 读取 raw_observations、用户反馈、环境状态
    ↓
[规划模块] 决定下一步做什么（生成报告？推荐书架？提醒？追问？）
    ↓
[工具调用] 执行具体动作（analyze / search_bookshelf / add_cooldown / chat）
    ↓
[反思模块] 评估结果，更新记忆
    ↓
输出到前端 / 扩展 / 用户
```

### 3.2 记忆系统（Memory）

Agent 必须能记住用户，否则就是一次性工具。

至少两层：

| 记忆类型 | 存储内容 | 技术方案 |
|---|---|---|
| 短期记忆 | 当前对话上下文、本次会话的观察 | 进程内 + 数据库 |
| 长期记忆 | 用户兴趣变化、盲区历史、反馈偏好、认知趋势 | SQLite + 可能引入向量存储 |

### 3.3 调度系统（Scheduler）

替代 OpenClaw 的 cron skill。

- 定时生成周报告；
- 定时检查冷静期到期；
- 根据用户行为触发主动提醒（例如连续刷 30 分钟同质化内容）。

可用 Python 的 `APScheduler` 或自己写一个轻量调度循环。

### 3.4 工具调用层（Tools）

把原来的 4 个 Skill 变成 Agent 可调用的工具：

| 工具 | 对应原 Skill | 功能 |
|---|---|---|
| `analyze_cognition` | `analyze-cognition` | 生成认知体检报告 |
| `search_parallel_views` | `search-parallel-views` | 基于盲区推荐书架内容 |
| `socratic_dialog` | `socratic-dialog` | 苏格拉底式追问 |
| `cooldown_unlock` | `cooldown-unlock` | 冷静期到期解锁 |
| `add_cooldown` | （原 FastAPI 接口）| 添加冷静期条目 |

每个工具需要：
- 输入 Schema
- 执行函数
- 输出格式化
- 错误处理

### 3.5 用户模型（User Model）

Agent 需要理解用户：

- 用户偏好哪些话题？
- 用户对什么类型提醒敏感？
- 用户过去接受/拒绝了哪些建议？
- 用户的认知趋势是变好还是变坏？

这部分是 Agent 「智能」的核心，也是最难的部分。

### 3.6 多模型抽象层（LLM Provider）

通过配置切换模型：

```python
class LLMProvider:
    def chat(self, messages, tools=None, json_mode=False) -> str: ...

class DeepSeekProvider(LLMProvider): ...
class OpenAIProvider(LLMProvider): ...
class OllamaProvider(LLMProvider): ...  # 本地模型
```

用户配置：

```toml
[llm]
provider = "deepseek"
api_key = "..."
model = "deepseek-chat"
```

### 3.7 对话管理增强

苏格拉底追问要从「单次问答」升级为「多轮有记忆的对话」：

- 记住本轮对话主题；
- 能引用之前的报告/书架内容；
- 在对话中触发工具（例如："帮我把这个链接加入冷静期"）。

## 四、工作量评估

**团队**：2 人，大一零基础，vibe coding 模式（Claude + Copilot）
**节奏**：课余时间，不赶 deadline

| 阶段 | 内容 | 预估时间 |
|---|---|---|
| **Phase 1：解耦 OpenClaw** | 把 4 个 Skill 改成普通 Python 模块，FastAPI 可直接调用 | 2~3 周 |
| **Phase 2：Agent 运行时** | 实现观察-计划-行动-反思循环，工具调用层 | 3~4 周 |
| **Phase 3：记忆与用户模型** | 长期记忆、用户偏好学习、认知趋势 | 3~4 周 |
| **Phase 4：调度与主动性** | 定时任务、事件触发、主动提醒 | 2~3 周 |
| **Phase 5：多模型与打包** | LLM Provider、Ollama 本地支持、一键启动脚本 | 2~3 周 |
| **Phase 6：验证与打磨** | 端到端测试、 prompt 调优、文档更新 | 2~3 周 |

**总计**：约 **3~5 个月**（两人兼职）。

## 五、可行性评估

| 维度 | 评估 | 说明 |
|---|---|---|
| **技术可行性** | **高** | 不需要造通用框架，只需要为 EatWhat 这个场景实现 Agent 循环 |
| **学习可行性** | **中高** | 需要学习 ReAct、记忆系统、工具调用等概念，但 bounded 在一个场景内 |
| **时间可行性** | **中** | 3~5 个月不赶 deadline，可接受 |
| **团队可行性** | **中** | 需要 F 同学理解并配合前端改造，后端由 Claude 辅助 |
| **出彩可能性** | **高** | 自包含 + 垂直场景 + 长期记忆 + 主动性，比 API 调用应用有区分度 |

**总体结论：可行，但比简单修 bug 复杂得多。**

## 六、可能遇到的较大困难

### 6.1 Agent 行为不可控

LLM 会：
- 调用错工具；
- 生成错误参数；
- 陷入循环；
- 产生幻觉结论。

**应对**：每个工具都要有严格的输入校验；Agent 循环要有最大步数限制；重要结论要求 LLM 提供 evidence。

### 6.2 记忆系统设计困难

记忆不是简单存历史记录，而是要让 Agent 「知道什么重要、什么不重要」。

**应对**：先简单做（按时间衰减 + 关键词摘要），再逐步升级。

### 6.3 主动性 vs 不打扰的平衡

Agent 太主动会烦人，太被动就没意义。

**应对**：默认不打扰，只在高置信度场景下主动；用户可配置提醒频率。

### 6.4 Prompt 维护成本高

工具多了之后，每个工具的 prompt 都要调。

**应对**：建立 prompt 版本管理和简单评估集。

### 6.5 重构期间代码双轨运行

一边改 Agent 运行时，一边要保证现有功能不崩。

**应对**：小步快跑，每次 commit 都保留可运行状态；先复制再替换，不要直接删旧代码。

### 6.6 前端工作可能被低估

主动提醒、对话历史、趋势图、设置面板都需要前端改造。

**应对**：提前跟 F 同学同步，不要等后端做完再让前端改。

## 八、一句话总结
